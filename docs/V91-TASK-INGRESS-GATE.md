# Task ingress gate – integration boundary

The task ingress gate authenticates the exact canonical payload bytes with a
provider-specific HMAC key and then applies the use-domain classifier from
`controller/use_policy.py`.

## Decision semantics

- `REJECT_UNAUTHORIZED`: signature is malformed/invalid or no usable provider key exists.
- `REJECT_INVALID`: payload shape or canonical serialization is invalid.
- `BLOCK`: a signed declaration names a restricted use domain.
- `REVIEW_REQUIRED`: unknown/missing domain, civilian domain, or critical-supply sector.
- Every result has `execution_authorized=False`. This module does not execute,
  enqueue, isolate, or persist tasks.

## Security limits

- HMAC authenticates possession of a shared secret for the exact bytes. It does
  not establish legal identity, benign intent, or truth of the purpose claim.
- Provider keys must be supplied by an external secret manager with rotation
  and revocation. No production key provider is included.
- The JSON profile is UTF-8 with sorted keys, compact separators, Unicode
  preserved, and NaN rejected. It is a project-specific deterministic profile,
  not a claim of RFC 8785/JCS conformance.
- Keyword matching is deliberately not treated as a security boundary.
- The current offline worker consumes locally written queue files and has no
  authenticated network ingress. This primitive is therefore not yet wired
  into that worker or any running API service.

## Required work before runtime integration

1. Define and authenticate the actual ingress transport and provider identity.
2. Connect a managed key provider with rotation, revocation, and audit evidence.
3. Define a separate human-review approval object, signer, expiry, and replay
   protection. A review decision must not be inferred from a label.
4. Persist decisions through the existing ledger interface and independently
   anchor the head if stronger tamper evidence is required.
5. Integrate at the real queue/API boundary and test that rejected or pending
   tasks cannot reach execution.


## Replay protection (implemented primitive)

The gate now requires signed `timestamp` (integer Unix seconds) and `nonce`
(32–128 hexadecimal characters, at least 128 bits). The timestamp must be
within the configured clock-skew window (default: 300 seconds). After HMAC
verification and freshness validation, the gate atomically claims the
provider-scoped task ID and nonce in `SQLiteReplayStore`.

The SQLite store uses a transaction and uniqueness constraints for
(provider, task ID) and (provider, nonce), so concurrent processes sharing the
same supported local database cannot both claim the same identifier. Replay
rows are intentionally retained. Storage errors fail closed.

Limitations:
- The nonce must be generated by a cryptographically secure random generator
  at the sender; the receiver validates its shape but cannot prove randomness.
- Clock synchronization and operational time-source monitoring are external
  requirements.
- SQLite is a single-host local store, not a distributed replay database.
  Do not assume safe semantics on arbitrary network filesystems.
- Database backup, restore, access control, disk exhaustion, and retention
  require operational tests. Restoring an old database can reopen replay
  windows unless the database head/state is independently protected.
- This remains a decision primitive; the offline worker is not connected.
- A task ID is consumed once HMAC and freshness pass, even if later policy
  classification blocks it or sends it to review. Submit corrected work with
  a new task ID.

## State rollback protection (verification primitive)

`controller/state_monotonicity.py` verifies a challenge-bound Ed25519 heartbeat
from an independently operated witness. The signed payload binds the replay
database ID, witness epoch, sequence, state-root hash, issue time, and a fresh
256-bit challenge. The caller must generate a fresh challenge and obtain the
witness response for that exact challenge; previously captured signed
heartbeats therefore cannot be replayed as responses to a new challenge.

The local sequence is compared in the correct direction: if the witness
remembers a higher sequence than the restored local database, the result is
`ROLLBACK_DETECTED_SEQUENCE`. Equal sequence with a different root is
`STATE_ROOT_MISMATCH`. A local state ahead of the witness is also rejected
until the witness is advanced. Unknown keys, invalid signatures, stale
responses, challenge mismatch, and unavailable local state fail closed.

**Critical limitation:** this is not a distributed database and does not itself
contact or operate a witness. Security depends on an independently administered
witness that durably preserves its latest state and signs only fresh,
challenge-bound responses. If the witness can be rolled back, compromised, or
controlled by the same administrator as the SQLite host, the guarantee fails.
No automatic process isolation, database repair, or worker integration is
performed. The caller must refuse ingress on any failed verification result.

## SQLite replay-state provider

`controller/replay_state_provider.py` provides a local append-only replay
claim table compatible with the monotonicity guard's
`get_database_id()`, `get_last_logged_sequence()`, and
`compute_current_state_hash()` interface. Sequence numbers are assigned by
SQLite inside `BEGIN IMMEDIATE`; duplicate provider/task or provider/nonce
claims are rejected. The state hash is calculated from one explicit read
transaction, using a deterministic JSON representation and a stable ordering.
Timestamps are stored in UTC and read back as timezone-aware UTC values.

The default path is project-relative under `ledger/replay_guard.db`; callers
may inject a database path. Parent directories are created as needed.

**Integration boundary:** `ReplayStateProvider.claim(provider_id, task_id,
nonce)` implements the `ReplayStore` protocol structurally and can be
injected into `TaskIngressGate`. The new
`controller/replay_db_unification.py` provides an explicit migration from
the actual legacy `ingress_replay(provider_id, task_id, nonce, claimed_at)`
schema and a witness-first connector. These are integration primitives, not
automatic runtime wiring: the application must initialize one provider at the
chosen destination path, complete and verify migration before configuring the
gate to use that provider, and supply a fresh challenge plus a signed witness
response on each ingress attempt.

The migration leaves the source database untouched, imports rows under one
destination `BEGIN IMMEDIATE` transaction, preserves provider/task/nonce
identity and converts Unix timestamps to UTC. Exact existing identity
mappings are idempotently accepted; any conflicting task or nonce mapping
aborts the complete migration. A source fingerprint is recorded in the
destination to make retries of an unchanged source snapshot idempotent. A
missing legacy table or incompatible schema fails closed. The migration does
not automatically switch a running worker's configured database.

The provider is local SQLite state, not distributed consensus, immutable
storage, or a substitute for the external signed witness. A restored database
is detectable only when compared with a newer independently retained witness
checkpoint. WAL and `synchronous=FULL` improve local durability semantics but
do not prevent privileged filesystem rollback or guarantee hardware-level
persistence.


## Witness-first ingress connector (integration primitive)

`VerifiedTaskIngressConnector` invokes
`V91StateMonotonicityGuard.verify_state_integrity` before calling
`TaskIngressGate.validate`. The caller must provide the expected fresh
challenge and configured trusted key ID. The connector checks that supplied
raw bytes exactly match the canonical serialization of the payload, then
returns the gate decision with `execution_authorized=False`. Witness failure,
payload mismatch, or unexpected validation errors return `GATE_CLOSED`.

No witness transport, challenge generator, worker/API attachment, automatic
queue blocking, or task execution is implemented here. The caller remains
responsible for obtaining a fresh challenge from an independently operated
witness and placing this connector at the actual task-ingress boundary.
